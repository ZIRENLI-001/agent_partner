# 复杂指令下的多轮对话评测系统方案

## 1. 赛题理解

赛题要求设计并实现一套针对已有任务指令的自动化指令遵循能力评估系统。业务背景是履约数字人外呼场景：系统自动发起与用户的通话，对话模型需要根据预设任务指令完成具体任务。由于任务指令包含流程、约束、FAQ 和异常分支，人工评估成本高，且难以稳定量化。

交付目标可以拆成两项：

- 构建用户模拟器，充分有效测试对话模型在特定任务指令下的效果。
- 自动产出评测报告，评测过程可解释，评测结果可量化。

因此，本方案不定位为通用 LLM 评测平台，也不定位为模型训练或自动优化系统，而是聚焦：

> 面向履约数字人外呼任务指令的自动化指令遵循评测系统。

## 2. 核心目标

系统输入一条已有任务指令，自动完成以下流程：


```text
任务指令
  -> 指令结构化解析
  -> 用户模拟场景生成
  -> 多轮对话测试
  -> 指令遵循评估
  -> 可解释量化报告
```

核心问题是回答：

- 模型是否完成了任务指令中的业务目标？
- 模型是否按照要求的流程推进？
- 模型是否遵守了字数、语气、边界、禁止行为等约束？
- 模型在用户拒绝、追问、打断、忙碌、越界问题下表现如何？
- 每个扣分项能否追溯到原始指令和具体对话轮次？

## 4. 系统方案

### 4.1 指令解析模块

指令解析模块将原始任务指令拆成结构化评测规格。

抽取内容包括：

- 角色设定。
- 任务目标。
- 开场白。
- 必须完成的流程步骤。
- FAQ 和知识点。
- 回复风格和长度约束。
- 禁止行为。
- 用户异常分支。
- 结束条件。

示例结构：

```json
{
  "task_goal": "通知骑手飞毛腿合同今日生效，并提醒完成配送任务",
  "required_steps": [
    "确认骑手身份",
    "告知合同今日生效",
    "询问是否可以开始配送",
    "说明单日/多日合同单量要求",
    "处理不想配送的骑手",
    "提醒注意安全"
  ],
  "constraints": [
    "每次回复约30字以内",
    "语气自然，符合电话沟通",
    "避免重复回复",
    "超出职责范围时说明确认后再回电"
  ],
  "edge_cases": [
    "骑手不想配送",
    "骑手询问退出方式",
    "骑手询问奖励",
    "骑手询问超出职责范围的问题"
  ]
}
```

### 4.2 用户模拟器

用户模拟器根据任务指令生成多类测试用户，并与待测模型进行多轮对话。用户模拟器的目标不是闲聊，而是充分覆盖任务指令中的关键分支。

用户模拟场景来源包括：

- 指令显式分支：例如用户不知情、用户不是负责人、用户开车、骑手不想配送。
- FAQ 分支：例如询问奖励、退出方式、价格差异、配置步骤。
- 约束分支：例如打断模型、要求模型简短回答、提出越界问题。
- 履约业务先验：例如骑手正在配送、担心恶劣天气、质疑派单公平性。

模拟器需要遵守以下约束：

- 保持用户角色一致。
- 不泄露评分标准。
- 不主动帮助模型完成任务。
- 不生成明显脱离任务指令的极端问题。
- 根据模型回复动态追问或结束。

### 4.3 多轮对话执行

对话执行模块负责控制测试过程：

- 输入任务指令、用户场景和待测模型接口。
- 用户模拟器和待测模型交替发言。
- 控制最大轮数和终止条件。
- 记录完整对话轨迹。

每条轨迹至少包含：

- 任务指令 ID。
- 用户模拟场景。
- 每轮用户发言和模型回复。
- 触发的任务分支。
- 结束原因。

### 4.4 自动评测模块

评测模块采用“规则校验 + LLM Judge”的混合方式。

规则校验用于确定性指标：

- 回复长度是否超限。
- 是否出现禁止承诺。
- 是否提到必需信息。
- 是否在用户开车或不便沟通时及时结束。
- 是否存在明显重复回复。

LLM Judge 用于语义指标：

- 是否完成任务目标。
- 是否按照流程推进。
- 是否准确回答 FAQ。
- 是否合理处理用户拒绝、追问、打断和越界问题。
- 是否符合电话沟通风格。

硬约束尽量由程序判断，语义项由 Judge 判断。这样可以降低纯 LLM 打分的不稳定性。

### 4.5 评测报告

报告必须同时满足可量化和可解释。

报告内容包括：

- 总分和维度分。
- 场景覆盖情况。
- 每个测试场景的通过/失败结果。
- 扣分项。
- 原始指令依据。
- 对话轮次证据。
- 失败原因。
- 改进建议。

可解释性采用三层证据链：

```text
原始任务指令依据 -> 对话轮次证据 -> 评分结论和扣分原因
```

示例：

```text
评测项：是否提醒多日合同每天完成 Y 单
指令依据：Knowledge Points 要求说明多日合同每天必须完成 Y 单
对话证据：第 4 轮模型仅说“记得高峰上线”
结论：未通过
扣分原因：遗漏每日单量要求
```

## 5. 量化指标

评分维度由任务指令动态生成，但可采用统一一级维度。

| 维度 | 说明 |
| --- | --- |
| 任务完成度 | 是否完成任务指令的核心业务目标 |
| 流程遵循度 | 是否按照指定流程和分支推进 |
| 约束遵循度 | 是否满足字数、语气、暂停、禁止行为等约束 |
| FAQ 准确性 | 是否准确回答指令中的知识点 |
| 异常处理能力 | 是否正确处理拒绝、打断、忙碌、越界问题 |
| 对话自然度 | 是否符合电话外呼口语风格 |
| 安全与边界 | 是否避免越权承诺、错误施压和不当回答 |

评分可采用 100 分制。对于严重违反指令的情况设置高风险标记，例如：

- 用户开车时仍持续长篇说明。
- 承诺未在指令中出现的奖励或优惠。
- 对超出职责范围的问题给出确定结论。
- 未确认身份就泄露敏感任务信息。

## 6. 模型选择与校准

系统涉及三类模型：

- 待测模型：被评估的对话模型。
- 用户模拟模型：扮演用户生成多轮测试输入。
- Judge 模型：辅助判断语义类评测项。

模型选择原则：

- 用户模拟模型需要角色一致、可控、不会泄露评分标准。
- Judge 模型需要结构化输出稳定、长上下文能力足够、评分与人工判断接近。
- 字数、禁词、必需字段、结束条件等硬指标不依赖 Judge。

Judge 可信度通过小规模人工标注校准：

```text
人工标注样本
  -> 候选 Judge 评分
  -> 对比人机一致性
  -> 选择主 Judge
  -> 优化 Rubric 和 Judge Prompt
```

在未拿到脱敏数据前，可用样例指令构造少量人工标注 case 验证链路；拿到脱敏数据后，再抽样真实对话校准用户模拟器和 Judge。

## 7. 参考技术与项目

本方案参考以下方向，但不会直接照搬为通用 Agent 平台：

- `tau-bench / tau2-bench`：参考用户模拟器、任务策略和多轮轨迹评测。
- `SOTOPIA`：参考角色卡、目标卡、场景卡构造交互测试。
- `G-Eval`：参考结构化 LLM 评估和评分理由生成。
- `MT-Bench / Chatbot Arena`：参考 LLM-as-Judge，同时注意偏差控制。
- `StructFlowBench`：参考多轮流程依赖和结构化任务评估。
- `MultiChallenge`：参考 instance-level rubric 的多轮对话评估。
- `MMMT-IF`：参考程序化指令遵循，把硬约束尽量转为规则校验。
- `Meeseeks`：参考美团指令遵循评测中的细粒度约束拆解。

## 8. MVP 范围

比赛 MVP 聚焦一个可跑通、可解释的完整闭环。

### 8.1 输入

- 1 条或多条任务指令。
- 待测对话模型接口。
- 用户模拟配置。

### 8.2 输出

- 结构化任务规格。
- 5 到 10 个用户模拟场景。
- 多轮对话轨迹。
- 自动评测结果。
- Markdown 或 HTML 评测报告。

### 8.3 演示重点

建议以飞毛腿骑手任务作为主演示：

- 正常确认合同生效。
- 骑手不想配送。
- 骑手询问奖励。
- 骑手询问退出方式。
- 骑手正在配送或不便长聊。
- 骑手提出超出职责范围问题。

展示系统如何生成场景、执行多轮对话、自动评分，并给出带证据的扣分原因。

## 9. 与比赛要求的对应关系

| 比赛要求 | 方案对应 |
| --- | --- |
| 构建用户模拟器 | 用户模拟器根据任务指令生成多类用户行为并进行多轮交互 |
| 充分有效测试模型效果 | 通过流程分支、FAQ 分支、异常分支和约束分支覆盖关键场景 |
| 自动产出评测报告 | 报告生成模块输出总分、维度分、扣分项和改进建议 |
| 评测过程可解释 | 每个结论绑定原始指令依据和对话轮次证据 |
| 评测结果可量化 | 使用统一一级维度和任务级 Rubric 生成 100 分制结果 |

## 10. 方案边界

为避免偏离赛题，当前阶段不把以下内容作为核心交付：

- 不做通用 LLM 评测平台。
- 不做模型训练或自动微调。
- 不直接接入真实外呼生产系统。
- 不把多模型排行榜作为主目标。
- 不把可视化看板作为必需能力。

这些能力可作为后续扩展，但比赛阶段以“用户模拟 + 自动评测报告”为主。

## 11. 总结

本方案聚焦官网赛题要求：针对已有复杂任务指令，构建自动化多轮对话评测系统。系统先将任务指令结构化，再生成用户模拟场景，与待测模型进行多轮交互，最后基于规则校验和 Judge 语义评估产出可解释、可量化报告。

核心创新点是：

- 从任务指令自动生成评测 Rubric。
- 用户模拟器按任务分支动态测试模型。
- 评测报告采用“指令依据-对话证据-量化扣分”的证据链。

该方案既贴合履约数字人外呼场景，也控制在比赛周期内可实现的范围。
