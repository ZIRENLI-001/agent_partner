# 复杂指令多轮对话自动评测平台项目介绍

## 一、项目概述

本项目是一套面向复杂任务指令的多轮对话自动评测平台，重点解决外呼数字人、客服助手、履约运营助手等场景中“模型是否真正按任务指令完成业务目标”的评测问题。

传统评测往往依赖人工抽检或单轮问答打分，难以覆盖复杂任务中的流程步骤、FAQ、异常分支、权限边界和多轮追问。本系统将任务指令自动拆解为可执行的评测链路，通过动态 Rubric、用户多场景模拟、多轮对话执行、规则与语义混合评测、质量门禁和可视化报告，形成从“输入任务”到“评测结论和优化建议”的闭环。

系统支持两种使用方式：

- 端到端快速评测：输入任务指令和模型配置后，一次性生成完整评测结果和报告。
- 分阶段评测：按“模型配置、样本导入、指令解析、Rubric、对话模拟、执行评测、报告分析”逐步推进，每一步可查看、校准和重跑。

## 二、项目要解决的核心问题

复杂外呼任务不是简单问答。一个合格的数字人需要同时满足多类要求：

- 完成业务目标，例如通知合同生效、确认订单延迟、解释产品差异、引导用户完成操作。
- 遵循流程，例如先确认身份，再说明来意，再处理用户追问。
- 准确回答 FAQ，例如奖励、退出方式、费用、配置步骤、配送规则。
- 遵守边界，例如不能承诺未授权奖励，不能编造政策，不能在用户开车时持续施压。
- 保持电话对话自然，避免重复、机械、角色混淆或过长回复。
- 在多轮对话中持续保持上下文一致。

如果只看最终回复或单一分数，无法判断模型到底哪里失败，也无法指导后续优化。因此本项目将评测拆成可解释的工程链路：每个分数都关联任务指令、评测项、对话轮次和失败原因。

## 三、整体评测链路

系统评测流程如下：

```text
任务指令 / 样本数据
  -> 指令结构化解析
  -> 动态 Rubric 生成
  -> 用户多场景模拟
  -> 多轮对话执行
  -> 规则评测 + 语义 Judge
  -> 质量门禁与自动修复
  -> 可视化报告与对比分析
  -> 链路优化建议
```

各模块职责如下：

| 模块 | 作用 |
| --- | --- |
| 指令解析 | 从原始任务中抽取角色、目标、流程、FAQ、约束、边界和异常分支 |
| Rubric 生成 | 为当前任务动态生成评测项，而不是套用固定模板 |
| 对话模拟 | 基于任务和样本库生成不同用户反应，驱动多轮测试 |
| 执行评测 | 控制被测模型与用户模拟器轮流发言，记录完整对话轨迹 |
| 规则评测 | 校验长度、禁用承诺、角色边界、明显遗漏等可程序化指标 |
| 语义 Judge | 判断语义类指令遵循、FAQ 准确性、异常处理和自然度 |
| 质量门禁 | 检查场景覆盖、Rubric 适配、Judge 漏评、证据追溯和耗时异常 |
| 报告分析 | 生成分数、维度、失败原因、证据链、对比和优化建议 |

## 四、动态评测指标

本项目的评测指标不是固定写死的，而是根据当前任务指令和样本数据动态生成。系统先解析任务目标、流程、约束和 FAQ，再生成与当前业务目标匹配的 Rubric。

### 1. 一级评测维度

系统支持统一的高层评测维度：

| 维度 | 说明 |
| --- | --- |
| 任务完成度 | 是否完成任务指令中的核心业务目标 |
| 流程遵循度 | 是否按要求完成身份确认、任务说明、确认反馈等步骤 |
| 约束遵循度 | 是否满足字数、语气、暂停、禁止行为等约束 |
| FAQ 准确性 | 是否准确回答任务指令中的知识点 |
| 异常处理能力 | 是否正确处理拒绝、忙碌、打断、追问、越界问题 |
| 安全与边界 | 是否避免未授权承诺、错误施压、虚构政策等风险 |
| 对话自然度 | 是否符合真实电话沟通习惯，避免重复和角色混淆 |
| 证据可追溯性 | 每个判断是否能定位到具体对话轮次和任务依据 |

### 2. 百分制标准化

不同任务的 Rubric 数量和权重可能不同。系统采用百分制标准化，让不同任务、不同模型、不同场景之间可以横向比较。

例如：

- 原始得分用于保留每个评测项的权重贡献。
- 标准化得分用于展示整体通过率。
- 关键失败项用于标记高风险问题，不让总分掩盖严重错误。

### 3. 质量指标

除模型得分外，系统还会评估“评测系统自身是否可靠”：

- 场景覆盖数量。
- 覆盖目标数量。
- 风险标签数量。
- 场景类型数量。
- 多样性得分。
- Judge 漏评数量。
- 证据轮次可追溯率。
- 报告完整性。
- 各阶段耗时异常。

这使平台不仅能评模型，也能评估本次评测结果是否可信。

## 五、用户多场景模拟

项目内置评测样本库，当前样本库会扩展到 1000 条样本，覆盖多个业务域、难度等级、场景类型、风险标签和 expected_labels。样本库包含：

- 业务域：`meituan_fulfillment`、`course_publishing`、`fulfillment_ops`、`merchant_fulfillment`、`customer_fulfillment`。
- 难度等级：L1 到 L5。
- 场景类型：订单确认、商家出餐延迟、地址异常、售后边界、ETA 解释、课程直播选项、低延迟直播、优惠边界、第三方配置、恶劣天气、安全挂断等。
- 风险标签：安全边界、越权承诺、价格解释、用户打断、低延迟直播、调度协作、商家延迟、路线异常等。
- expected_labels：每条样本保留预期 verdict、原因和证据轮次，用于评测系统自检。

### 1. 模拟不同用户反应

系统不是简单生成“标准用户问题”，而是模拟多类真实用户反应：

- 用户配合，正常完成确认。
- 用户忙碌，需要简短说明或后续回访。
- 用户拒绝执行任务，需要挽留或边界处理。
- 用户追问 FAQ，例如奖励、费用、退出、配置步骤。
- 用户挑战规则，例如质疑派单、质疑费用、质疑系统责任。
- 用户提出越界诉求，例如要求承诺优惠、承诺免罚、承诺排名。
- 用户处于特殊状态，例如开车、恶劣天气、配送压力大。

### 2. 防止角色混淆

用户模拟器与被测模型是隔离的两个角色。系统在工程链路中对用户模拟输出做校验，避免用户模拟器复述数字人话术、替数字人推进任务或出现角色混淆。用户模拟器只扮演被外呼对象，围绕当前场景给出自然反应。

### 3. 场景种子校验

系统对生成的 `initial_user_intent`、覆盖目标和风险标签进行结构化校验，避免坏场景种子进入后续多轮对话。这样可以从源头提高用户模拟质量。

## 六、端到端快速评测

端到端快速评测适合评委演示、模型快速验收和日常 smoke test。

用户只需要提供：

- 任务指令。
- 待测模型配置。
- 场景数量或导入数据。

系统自动完成：

1. 指令解析。
2. Rubric 生成。
3. 用户场景生成。
4. 多轮对话执行。
5. 自动评分。
6. 质量分析。
7. 报告生成。

端到端模式的价值是降低使用门槛：非算法同学也可以快速得到一份完整评测报告，用于判断模型在当前任务上是否可上线、是否需要继续优化。

## 七、分阶段评测

分阶段评测面向专家调试和算法优化。它把评测链路拆成可观察、可校准、可重跑的多个阶段：

| 阶段 | 能力 |
| --- | --- |
| 模型配置 | 设置被测模型和后端评测链路模型 |
| 样本导入 | 从样本库或表格导入业务数据 |
| 指令解析 | 查看任务目标、角色、流程、约束和 FAQ 是否解析正确 |
| Rubric 生成 | 查看当前任务的评测项、权重、关键失败项 |
| 对话模拟 | 查看多种用户反应和测试重点 |
| 执行评测 | 运行多轮对话并生成证据 |
| 报告分析 | 输出量化指标、质量摘要和优化建议 |

分阶段模式支持：

- 每一步查看中间产物。
- 对关键阶段进行重新生成。
- 选择特定场景运行。
- 从当前步骤跳转。
- 发现质量门禁失败后由后端自动重试或补判。

这使系统不仅能“给一个结果”，还能支持评测链路调试。

## 八、评测报告可视化

系统提供 React 可视化页面，报告不只是 Markdown 文本，而是包含多层可解释信息。

### 1. 总览指标

报告页展示：

- 总分。
- 通过率。
- 质量状态。
- 证据可追溯率。
- Judge 漏评数量。
- 场景多样性得分。

### 2. 维度与场景视图

报告支持：

- 维度得分进度条。
- 场景覆盖矩阵。
- 单场景得分。
- 关键失败项。
- 对话轨迹切换。
- 评判标准、实际表现和证据轮次。

### 3. 证据链

每个失败项都尽量保留三层证据：

```text
任务指令依据 -> 对话轮次证据 -> 评分结论与扣分原因
```

评委可以直接看到：

- 该评测项来自哪类任务要求。
- 模型实际在哪几轮没有满足要求。
- Judge 为什么判定为 fail、partial 或 needs_review。

### 4. 质量摘要

报告中还包含“评测系统可靠性”信息，包括：

- 场景覆盖是否足够。
- Rubric 是否适配当前任务。
- Judge 是否漏评。
- 证据轮次是否可追溯。
- 报告是否完整。
- 哪些阶段耗时异常。
- 是否触发自动修复。

这部分用于回答评委最关心的问题：这次评测本身是否可信。

## 九、历史评测、对比分析与优化建议

系统保存每次 run 的完整产物，包括：

- `task_spec.json`
- `rubric_spec.json`
- `scenarios.json`
- `traces.jsonl`
- `evaluation_results.json`
- `quality_summary.json`
- `stage_timings.json`
- `report.md`

历史页支持按任务、模型和场景查看记录，并提供对比分析。

### 1. 对比方式

支持两类横向对比：

- 同一场景不同模型：适合比较多个模型谁更稳定。
- 同一模型不同场景：适合发现某个模型在哪些业务场景薄弱。

对比表展示：

- Run ID。
- 模型名称。
- 场景 ID。
- 得分。
- 通过率。
- 关键失败数量。
- 保存时间。

### 2. 失败原因汇总

系统会把当前筛选范围内的失败项聚合展示，支持展开和滑动查看。失败原因不只展示“没通过”，还会说明涉及模型、场景和示例 run，方便评委跳转到完整报告。

### 3. 三段式优化建议

系统把失败原因进一步转化为优化建议，并按三段式展示：

| 字段 | 说明 |
| --- | --- |
| 问题判断 | 当前失败更像是提示词问题、算法链路问题、样本数据问题、模型配置问题还是业务流程问题 |
| 证据指向 | 影响了多少场景、多少评判项、多少证据，以及关联的业务上下文 |
| 下一步动作 | 给出明确可执行的优化方向，例如补充必答清单、修正 Rubric、补齐样本标签、增加 Judge 补判 |

这使评测报告从“指出问题”进一步走向“指导优化”。

## 十、评测系统可靠性设计

本项目不仅评估被测模型，也评估评测链路本身。

### 1. 样本库自检

样本库中的 expected_labels 可用于 evaluator 自检：

- 标准标签一致率。
- critical 项误判。
- 证据轮次命中率。
- 样本得分区间合理性。

这让系统可以验证 Judge 和规则评测是否稳定，而不是完全相信模型裁判。

### 2. Judge 完整性检查

系统会检查：

- 应评 Rubric 项数量。
- 实际观察到的 evidence 项数量。
- Judge 漏评项。
- 分数溢出项。

如果 Judge 没有返回某个评判项，系统会标记漏评，并可触发补判或质量门禁。

### 3. 证据可追溯检查

每条 evidence 都应引用具体 turn_id。系统会检查引用的轮次是否存在，计算证据可追溯率。如果某条评分没有有效对话证据，报告会提示可信度风险。

### 4. Rubric 适配检查

Rubric 不是固定模板。系统会根据当前任务生成专属 Rubric，并检测生成结果是否过于模板化或与任务不匹配。对于不匹配的 Rubric，系统会进入质量门禁或触发重新生成。

### 5. 耗时与链路健康

系统记录每个阶段耗时：

- 指令解析。
- Rubric 生成。
- 对话模拟。
- 场景执行。
- 报告生成。

如果某阶段耗时为 0 或超过阈值，系统会标记为异常，避免“看似完成但实际没有调用模型”的情况。

| 页面 | 文件 | 作用 |
| --- | --- | --- |
| 首页 | `frontend/src/pages/HomePage.tsx` | 展示入口和评测流程 |

### 3. 模型角色隔离

系统支持多个模型角色：

- target_model：被测模型。
- user_simulator：用户模拟模型。
- semantic_judge：语义裁判模型。
- rubric_generator：Rubric 生成模型。
- scenario_generator：场景生成模型。
- instruction_parser：指令解析模型。
- report_generator：报告生成模型。

模型角色隔离可以避免被测模型和用户模拟、Judge 混在一起，提高评测链路可控性。

## 十二、项目创新点

### 1. 从固定题目评测升级为动态任务评测

系统不是拿固定题库打分，而是根据任意输入任务指令动态解析目标、流程、FAQ 和边界，并生成专属 Rubric。

### 2. 从单轮问答升级为多轮用户模拟

系统模拟真实用户在多轮通话中的反应，包括拒绝、追问、忙碌、质疑、越界诉求和异常状态，更接近真实外呼业务。

### 3. 从单一得分升级为证据链评测

每个扣分项都尽量关联任务依据、对话轮次、预期行为、实际表现和判定解释，评委可以追溯分数来源。

### 4. 从报告展示升级为链路质量控制

系统会检查 Rubric 适配、Judge 漏评、证据可追溯、报告完整性和耗时异常，避免低质量评测结果直接被采信。

### 5. 从失败原因升级为优化决策

历史对比中不仅展示失败原因，还会归因到提示词、算法链路、样本数据、模型配置或业务流程，并给出“问题判断、证据指向、下一步动作”。

### 6. 从黑盒评测升级为分阶段可调试

分阶段评测让评审和算法同学可以看到每一步中间产物，定位问题发生在指令解析、Rubric、对话模拟、执行评测还是报告分析。

### 7. 从单业务样例升级为多业务样本库

样本库覆盖履约、商家、客户、课程发布、调度协作等多类场景，支持多难度、多风险标签和 expected_labels 校准。

## 十三、评委演示建议路径

建议按以下顺序演示：

1. 首页  
   展示系统支持端到端快速评测、分阶段评测和历史评测。

2. 端到端快速评测  
   输入一条复杂任务指令，快速生成完整报告，展示自动化能力。

3. 分阶段评测  
   展示指令解析、Rubric、对话模拟、执行评测、报告分析的中间产物，说明系统可调试。

4. 样本库  
   展示多业务域、多难度、多覆盖目标和 expected_labels，说明评测有校准基础。

5. 报告详情  
   展示总分、维度分、场景得分、对话轨迹、失败证据链和质量摘要。

6. 历史对比  
   展示同一场景不同模型、同一模型不同场景的对比。

7. 优化建议  
   展示三段式建议：问题判断、证据指向、下一步动作，说明系统能指导算法、提示词和数据优化。

## 十四、总结

本项目的核心价值是把复杂指令对话评测从“人工主观判断”转化为“自动化、可解释、可追溯、可对比、可优化”的工程系统。

它不仅能回答“模型得了多少分”，还能回答：

- 测了哪些用户场景？
- 哪些任务要求没有完成？
- 失败证据在哪一轮对话？
- 当前评测结果是否可靠？
- 应该优化提示词、算法链路、样本数据、模型配置还是业务 SOP？

因此，本项目适合作为复杂业务数字人上线前的自动化验收工具，也适合作为模型迭代过程中的评测与诊断平台。
