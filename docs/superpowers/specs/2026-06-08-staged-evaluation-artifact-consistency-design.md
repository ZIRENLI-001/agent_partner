# Staged Evaluation Artifact Consistency Design

## Goal

Ensure the staged evaluation wizard executes the exact `TaskSpec`,
`RubricSpec`, and `ScenarioSet` that the user reviewed and selected. Prevent
empty scenario selections from producing misleading zero-score reports.

## Confirmed Failure

The staged wizard currently calls three preview endpoints:

1. `/api/stages/parse`
2. `/api/stages/rubric`
3. `/api/stages/scenarios`

The run request only sends the raw instruction, input data, and selected
scenario IDs. The asynchronous worker regenerates all three artifacts. Model
generation is nondeterministic, so regenerated scenario IDs can differ from the
preview IDs. The engine then filters regenerated scenarios by stale preview
IDs, producing an empty `ScenarioSet`.

Production runs `run_a0cb646c` and `run_8d1f2308` demonstrated the failure:

- scenario generation reported five scenarios;
- the persisted scenario set contained zero scenarios;
- target, user simulator, and semantic judge model-call counts were zero;
- the report generator still created a zero-score report.

The same boundary also means edits made in the staged wizard are ignored by the
final evaluation.

## Design

### Request Contract

`RunRequest` gains three optional fields:

- `task_spec`
- `rubric_spec`
- `scenario_set`

They use the existing Pydantic domain models. Quick evaluation callers may omit
all three fields and retain the current model-generated pipeline.

The staged wizard sends the latest valid artifacts displayed in the editor. It
filters `scenario_set.scenarios` to the currently selected IDs before
submission. This makes the submitted scenario set the authoritative execution
input.

### Engine Execution

`run_full_evaluation()` accepts optional confirmed artifacts:

- a confirmed task skips instruction parsing;
- a confirmed rubric skips rubric generation;
- a confirmed scenario set skips scenario generation.

Skipped stages still receive timing entries, progress callbacks, and
diagnostics. Their diagnostics use `output_source="confirmed_stage_artifact"`,
`model_attempted=false`, and `fallback_used=false`.

When a confirmed scenario set is supplied, the engine validates that:

- its `task_id` matches the confirmed or generated task;
- its scenario list is not empty;
- selected IDs, if also supplied, match at least one scenario.

An empty result raises `ValueError` before scenario execution and report
generation. The asynchronous run status becomes `failed` instead of persisting
a misleading zero-score report.

### Queue Compatibility

Production requests are serialized through Redis. The new artifact fields are
plain JSON objects generated by Pydantic and are restored by
`RunRequest.model_validate()` in the worker. Existing queued payloads without
these fields remain valid.

### Diagnostics

Confirmed artifacts do not claim fresh model calls during the final run. The
run artifact records their origin explicitly. Scenario execution and report
generation continue to record the actual configured models and prompts.

This distinguishes:

- preview-stage model calls used to create reviewed artifacts;
- execution-stage model calls used for dialogue, judging, and reporting.

## Error Handling

- Invalid artifact schemas return HTTP 422 before queue submission.
- Mismatched task IDs fail the worker with a bounded public error.
- Empty confirmed scenarios fail the run before model execution.
- Quick evaluation without confirmed artifacts preserves existing generation,
  retry, and fallback behavior.

## Verification

1. A regression test reproduces stale selected IDs producing zero scenarios.
2. A test proves confirmed artifacts bypass parser, rubric, and scenario
   providers and are persisted unchanged.
3. A test proves empty or nonmatching confirmed selections fail before report
   generation.
4. A queue test proves confirmed artifacts survive request serialization.
5. Frontend tests prove the staged wizard sends reviewed artifacts.
6. Full backend tests and the frontend production build pass.
7. A real staged production run persists the same scenario IDs submitted by the
   wizard and records non-zero target, user simulator, judge, and report calls.
